# ElectronicMethodIR

`ElectronicMethodIR` is the method-neutral orchestration layer above the
existing scientific IRs. It describes how HF, Kohn-Sham DFT, and coupled-cluster
methods are assembled without taking ownership of their equations or runtime.

The first slice is intentionally representation-only. Constructing one of these
graphs does not change any production execution path, select CUDA/CPU kernels,
allocate workspace, or grant a method capability.

## Layering

```text
ElectronicMethodIR
  |
  +-- persistent state
  +-- operator dataflow
  +-- energy ownership
  +-- fixed-point iteration contract
  +-- optional response / derivative contracts
  |
  +-- composition_identity ------> existing DFT MethodIR
  +-- OperatorSpec.ir_identity --> existing TensorIR or other lower-level IR
```

Existing DFT `MethodIR` remains the canonical owner of XC/exchange/correction
composition. It is not renamed or repurposed by this layer. The common graph
stores only its semantic identity.

Likewise, RCCSD equations stay owned by the existing TensorIR generated by
`tools.vibeqc_cc.doubles.build_ccsd_program`. The orchestration layer references
that program through its logical hash instead of copying the equations.

## Initial producers

### RHF

`rhf_electronic_method_ir()` describes the restricted SCF fixed point:

```text
density
  -> build_fock
  -> diagonalize_fock
  -> build_density
  -> density_residual
```

The method records the current shared-SCF contract, but does not execute it.

### RKS

`rks_electronic_method_ir(method)` accepts the existing restricted DFT
`MethodIR`. The initial admitted domain is semilocal XC with optional
full-range exact exchange, covering PBE and PBE0-style graphs.

The resolved DFT composition is referenced through `composition_identity`;
individual Hartree, XC, and exact-exchange orchestration nodes do not pretend
to own a lower-level IR unless one is explicitly supplied later.

### RCCSD

`rccsd_electronic_method_ir(program)` accepts an audited RCCSD TensorIR program
that exposes:

- `correlation_energy`
- `singles_residual`
- `doubles_residual`
- live `t1` and `t2` state inputs

The equations node retains `program.logical_hash` as its lower-level IR
identity. The amplitude update remains a separate orchestration node so solver
policy is not confused with the TensorIR equations.

## Validation

Construction is fail-closed. The graph rejects:

- duplicate states, sources, operator names, or operator outputs;
- operator outputs that shadow persistent state or external sources;
- dangling operator inputs;
- self-dependencies and operator dependency cycles;
- energy outputs not owned by a declared operator;
- iteration residual/update values that are not operator outputs;
- iteration or response contracts referring to undeclared state.

Inputs, outputs, states, and operators are canonicalized before hashing.
`identity` is a structural hash independent of the descriptive method name,
while `manifest_identity` also includes the identifier. This lets aliases share
compiler cache identity without losing provenance.

## Non-goals of this slice

This change does not:

- replace the existing DFT `MethodIR`;
- lower HF/KS production runtime through the compiler;
- replace SCF or CCSD solvers;
- choose DF versus direct ERI providers;
- unify CUDA workspace ownership;
- publish new energy, force, or Hessian capabilities.

Those are subsequent lowering/integration steps. The purpose here is to establish
one validated top-level contract before those execution paths converge.
