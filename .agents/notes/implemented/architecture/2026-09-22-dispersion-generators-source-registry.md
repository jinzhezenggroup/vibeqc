# Decision: dispersion generators consume the common source registry

Status: implemented
Date: 2026-09-22

## Problem

The common scientific source registry pinned DFT-D4, multicharge, mctc-lib and
simple-DFTD3 inputs, but the D4/EEQ/gCP generators still carried independent
revision, license, path-inventory or output-revision constants. Those duplicate
owners could drift while the registry and checked-in products remained
internally self-consistent.

## Decision

Bind each executing generator and canonical input to its named registry product
and exact ordered source IDs.
DFT-D4 and EEQ read only explicitly synchronized cache files after validating
their registered SHA-256 and optional size. The DFT-D4 source collection owns
the historical parser order, and registered Git blob/tree metadata preserves
the existing output manifests without consulting an external Git checkout.

The gCP generator continues to lower the checked-in canonical H-Ar input, but
it validates that input's repository, revision, license and three source hashes
against `simple-dftd3-gcp` before rendering the header. Normal generation does
not fetch the network; `sync` and `update --revision` remain explicit maintainer
operations.

## Rejected alternatives

- Keeping generator-local revisions would leave two authorities for one source.
- Letting generators clone or follow upstream would break offline builds and
  make regeneration depend on a moving branch.
- Blessing newly generated hashes without comparing the bytes would hide
  formatting, platform-libm or scientific-data drift.

## Invariants

- Missing source IDs, changed revision/file/Git identity, stale generator or
  canonical-input bytes, and stale checked-in outputs fail closed.
- The D4, EEQ and gCP numerical parameters, method identities and checked-in
  generated bytes remain unchanged by this ownership migration.
- GFN1/GFN2 catalogs, basis/ECP, Libxc/XC, and Rys runtime and table-generator
  consumers remain outside this slice.

## Evidence

The registry tests exercise missing inputs, changed revisions and hashes,
corrupted cached bytes, and stale generator/product files. Regeneration hashes
are compared with the pre-migration Git blobs; the normal offline registry and
domain test suites remain the acceptance gates.

## Consequences

Maintainers synchronize the pinned remote file sets before D4/EEQ regeneration
instead of supplying arbitrary Git repositories and revisions. A reviewed
source update leaves product input identity stale until it is explicitly staged
for candidate generation. Output hashes remain unchanged until regenerated
bytes are reviewed and recorded.

## Revisit when

Revisit only if a new source kind cannot be represented by pinned file sets and
deterministic canonical inputs without introducing build-time network access.
